# 컴포넌트 구조 정리

특정 페이지/도메인 폴더를 전수조사해서 정리한다.
`company-folder-structure`가 "새 파일을 어디에 둘지"라면, 이 skill은 "이미 있는 구조를 어떻게 정리할지"다.

> **참조 표기:** 기준끼리는 번호가 아니라 이름으로 가리킨다(예: 「중복·반복 통합」, 「style·로직 불변」). 순서가 바뀌어도 참조가 깨지지 않게 하기 위함이다.

## 대원칙

- **목적은 가독성·유지보수성 고도화다.** 용도/로직이 같은 것끼리 묶이도록 정리하되, **파일 분리 자체가 목적이 아니다** — 재사용성 없고 의미 없는 사소한 조각까지 억지로 분리해 오히려 가독성을 해치지 않는다. 뭉쳐 있어 알아보기 어려운 코드를 가시성 좋게 정리하는 것이 핵심이다.
- **「style·로직 불변」이 최우선 게이트다.** 아래 모든 기준은 이 원칙 아래에서만 적용된다 — style이나 동작이 바뀔 위험이 있으면 그 기준보다 불변 원칙이 이긴다.
  - style이나 로직은 절대 바뀌면 안 된다.
  - **예외(구조상 불가피):** inline 컴포넌트를 분리하면서 부모 스코프 변수를 클로저로 참조하던 부분은 props로 승격할 수 있다. 단 **동작은 완전히 동일**해야 하며, 값/타이밍/렌더 결과가 달라지면 안 된다. 이 외의 로직 변경은 금지.
- **모든 정리 기준은 깊이와 무관하게 하위 컴포넌트에 재귀 적용된다.** 최상위뿐 아니라 자식, 그 자식의 자식까지 같은 기준으로 정리한다. 단 이는 **기준의 적용 범위**를 말하는 것이지 디렉토리 중첩을 늘리라는 뜻이 아니다 — `components/` 아래 디렉토리는 **2단계까지만** 둔다(「단독 컴포넌트 재배치」 참조).
- **기본은 제안 후 수정이다.** 전수조사 결과와 수정안을 먼저 제시하고, 합의된 범위로 실제 수정까지 수행한다. "검토만/제안만" 요청이면 제안 단계에서 멈춘다. "바로 정리/수정해줘"면 제안 요약 후 곧장 수정까지 진행한다.
- **분석만 하고 끝내지 않는다.** 하위 디렉토리까지 포함해 전수조사한다. 일부만 보고 전수조사라고 하지 않는다. 누락이 보이면 직접 끝까지 따라가서 정리한다. 작업 중 새로 생긴 단독 사용 컴포넌트도 다시 부모 하위로 정리한다.
- `리팩토링 해줘`처럼 대상 범위만 주어진 일반 요청에도 이 규칙으로 동작한다("구조" 리팩터링에 한정하지 않는다).

## 정리 기준 (무엇을 정리하나)

### constants / utils 위치 (도메인 vs common)

- 전수조사해서 중복·사용처를 파악한다.
- **한 도메인/페이지(예: industry)에서만 쓰이고 다른 곳에서 재사용하지 않으면 → 해당 도메인 내부**(`features/industry/constants` · `features/industry/utils`)에 둔다.
- **서로 다른 라우트(페이지) 2개 이상에서 쓰이면 → common으로 승격**한다. 목적지 판단:
  - 여러 feature/페이지가 공유하는 도메인성 로직·상수 → `features/common/{utils|constants}`
  - feature와 무관한 순수 함수 → `src/utils`
  - feature와 무관한 전역 상수 → `src/constants`
- 단일 페이지 전용 코드를 common으로 올리지 않는다(과도한 공용화 금지).
- **constants·utils 모두 같은 기준**(한 페이지 전용 → 도메인, 라우트 2개 이상 → common)으로 관리한다.
- **util성 함수는 컴포넌트 파일 안에 두지 않는다:** 컴포넌트 `index.tsx`의 모듈 레벨/상단에 선언된 포매터·빌더·변환·정규화 등 JSX를 그리지 않는 순수 함수(예: `formatOptional*`, `buildXxxOption`, `normalizeXxxName`, `toXxxItem`)는 **단 한 곳에서만 써도 `utils/`로 옮긴다.** 컴포넌트 본문에 util을 새로 만들지 않는다.
- **단일 사용 util은 "소비 컴포넌트/탭 이름의 도메인 util 파일 하나"로 묶는다:** 함수마다 파일을 쪼개지 말고, 그 util을 쓰는 컴포넌트/탭 이름의 단일 파일(`features/{domain}/utils/{componentOrTab}.ts`)에 모은다. 기존 선례 네이밍을 따른다(예: `rndTab.ts`, `concentrationDetailPanel.ts`). 탭처럼 이름이 겹칠 수 있으면 도메인/맥락 접두사로 유일하게 짓는다 — **소비 컴포넌트/탭 이름과 파일명을 일치**시킨다(예: 벨트 supplyTab → `beltSupplyTab.ts`, 특화단지 supplyTab → `specializationSupplyTab.ts`)(「이름 유일성」 준용). 2개 이상 컴포넌트가 공유하면 도메인 공용 util(포매터류는 `utils/format.ts` 등)로, 라우트 2개 이상이면 common으로 승격한다.
- **utils 사이드이펙트 주의:** formatter 등 프로젝트 전반에서 공용으로 쓰이는 util은 위치를 옮기거나 시그니처를 바꾸면 광범위한 영향이 생길 수 있다. **이동·변경 전에 사용처를 전수 확인해 영향 범위를 정리하고 먼저 컨펌을 받은 뒤** 실행한다. 실행 후에는 리포트에 **무엇을 어디로 옮겼는지·무엇을 바꿨는지**를 반드시 명시한다.
- util 함수 주석은 「주석 규칙」을 따른다.

### inline 분리 (map item · 섹션)

- 분리의 목적은 **가독성·재사용·유지보수**다. 갯수를 늘리려고 쪼개지 않는다.
- **분리한다:** 길거나 복잡한 inline component, 두 곳 이상에서 재사용되는 조각, 본문 흐름을 가리는 내부 helper component, 반복되는 inline tooltip content.
- **map의 return부 분리:** `array.map(...)`의 콜백이 **JSX를 반환**하면 그 항목(item)을 별도 컴포넌트로 분리한다. 리스트 렌더 한 건 한 건의 마크업을 부모 return부에 펼쳐 두지 않고, item 컴포넌트로 빼서 `map`은 그 컴포넌트를 렌더(props 전달)만 하도록 한다.
  - **필수 분리:** item이 ① 다중 형제/중첩 구조이거나 ② **로컬 파생값·조건 분기·이벤트 핸들러**를 포함하면 길이·복잡도와 무관하게 분리한다. (아래 (b) block-body 형태는 거의 항상 여기 해당한다 — 누락 1순위라 반드시 분리.)
  - **inline 허용(예외):** 단일 원시 태그에 텍스트·속성만 바인딩하는 trivial item(예: `arr.map(o => <option value={o.id}>{o.name}</option>)`, `<li>{x}</li>`, 구분자)은 굳이 분리하지 않는다(「대원칙」 과분리 금지). **단 같은 모양이 반복되면 「중복·반복 통합」 규칙으로 분리한다.**
- **두 가지 형태 모두 탐지 (놓침 방지):** 렌더 map은 두 형태가 있고 **둘 다 대상**이다.
  - (a) 화살표 직후 반환: `arr.map(x => <Row .../>)` 또는 `arr.map(x => (<Row/>))` — `.map(` 줄에서 바로 보인다.
  - (b) **block-body + 지연 return**: `arr.map((row, i) => { const a = …; const b = …; return (<tr>…</tr>); })` — 중간 로컬 변수 뒤 `return`이 아래쪽에 떨어져 있어 `.map(` 줄만 봐선 JSX 반환인지 안 보인다. **이 (b) 형태가 주 누락원이다.**
- **탐지 방법:** `.map(` 매칭 줄만 보고 판단하지 않는다. 각 `.map(` 호출의 **콜백 본문 끝(return)까지 따라가** JSX 반환 여부를 확인한다. 특히 콜백이 `=> {` 블록으로 열리면 안에 `return <…>` / `return (<…` 가 있는지 끝까지 본다. (block-body는 grep 1차에서 묻히므로 호출 단위로 트레이스한다.)
- **분리 시 처리:** 콜백 안의 로컬 변수(`importAmountText`, `shareText` 등 표시용 파생값)는 item 컴포넌트 내부로 옮기거나, 계산이 부모 의존이면 props로 승격한다(동작 불변, 「style·로직 불변」). `key`는 부모 map 쪽에 남긴다.
- **섹션 단위 분리:** 한 파일 안에서 **여러 섹션**(의미가 구분되는 화면 블록)이 함께 그려지면 각 섹션을 별도 컴포넌트로 분리한다. 부모는 섹션 컴포넌트들을 조합(배치)하는 역할만 하게 만든다.
- **섹션 분리 시 공유 스타일은 부모 style.ts:** 섹션을 분리하면서 섹션 간 **반복되는 스타일 코드**(gap·padding 등 레이아웃 일체가 동일)를 함께 분리해야 한다면, 그 스타일이 **다른 페이지에서는 반복 사용되지 않는다는 전제**하에 **부모 컴포넌트의 `style.ts`에 선언**하고, 하위 섹션 코드에서는 그 스타일을 **부모에게서 import해서 사용**한다. 동일 스타일을 각 하위 섹션마다 중복 선언하지 않는다. (스타일 선언 위치 일반 규칙은 「중복·반복 통합」을 따른다.)
- **반복 구조 묶음은 「중복·반복 통합」에서 다룬다:** 같은 모양의 마크업 묶음(헤더/타이틀 그룹 등)이 2회 이상 반복되면 작아 보여도 공통 컴포넌트로 추출한다 — 판정·스타일 위치는 「중복·반복 통합」 참조.
- **분리하지 않는다(inline 유지):** 한두 줄로 짧고, **반복되지 않으며**, 재사용되지 않고, 이름을 붙여도 의미가 늘지 않는 사소한 조각. 예) `<>{selectedYear}년 기준 3개년 연평균성장률(CAGR)</>` 같은 단순 tooltip content는 그대로 inline에 둔다.
- 분리하기로 한 inline tooltip content의 목적지: 순수 텍스트(여러 곳에서 재사용)면 도메인 `constants`, JSX를 포함하면 별도 컴포넌트.

### 중복·반복 통합 (컴포넌트·스타일·로직·타입 de-dup)

- 전수조사 시 constants/utils·type뿐 아니라 **컴포넌트·스타일 블록·로직(훅/함수)**의 중복·반복도 함께 찾아 무의미한 반복을 줄인다.
- **반복되는 구조 묶음(크기 아닌 반복이 기준):** 의미가 같은 마크업 묶음(예: `<S.SectionHeader><S.SectionTitle>…</S.SectionTitle></S.SectionHeader>` 같은 헤더/타이틀 그룹)이 **2회 이상 반복**되면 작아 보여도 공통 컴포넌트로 추출한다. 분리 기준은 "크기"가 아니라 "**반복**"이다 — 한두 줄이어도 같은 모양으로 여러 곳에 반복되면 분리 대상이다. 호출부는 텍스트·액션만 props로 넘기고, 같은 마크업을 여러 곳에 다시 펼쳐 두지 않는다.
- **중복 컴포넌트:** 구조·역할이 실질적으로 동일한 컴포넌트가 여러 곳에 따로 정의돼 있으면 하나로 통합한다. case별 미세 차이는 props/optional prop 분기(「case 분기는 props」)로 흡수하되, optional 기본값을 기존 동작과 동일하게 둬 기존 호출부는 불변으로 유지한다.
- **중복/반복 스타일 — 선언 위치:** 동일한 styled 블록이 여러 `style.ts`에 반복되면 **사용 범위에 따라 한 곳에만 선언하고 끌어다 쓴다** — 한 부모 트리 안이면 부모 `style.ts`, 같은 도메인 내 여러 트리면 도메인 공용 style, 라우트 2개 이상이면 common style로 승격(「constants/utils 위치」 준용). 같은 스타일을 파일마다 중복 선언하지 않는다.
- **중복 로직/훅:** 같은 데이터 패칭·상태·변환 로직이 복붙돼 있으면 커스텀 훅 또는 util로 추출해 공유한다(위치·승격은 「constants/utils 위치」, 추출 절차는 「훅 추출」 준용).
- **중복 타입:** 하위 컴포넌트들(중첩 포함)에서 여러 번 중복되는 타입은 `features/{feature}/types/` 용도별 `.ts` 파일로 분리해 재사용한다(「type 분리」 참조).
- **통합 vs 유지 판정:** 기준은 "**의미·구조·동작이 같은가**"다. 겉모습만 비슷하고 의미가 다르면 합치지 말고 분리 유지하며(「이름 유일성」), 미묘한 차이를 한 컴포넌트에 욱여넣어 분기 지옥을 만들지 않는다. 통합으로 가독성이 더 나빠지면 통합하지 않는다.
- **배치·승격:** 통합 결과물의 위치는 「constants/utils 위치」·「단독 컴포넌트 재배치」와 동일 — 한 페이지 전용은 도메인 내부, 라우트 2개 이상에서 쓰이면 common 승격. 단일 페이지 전용 코드를 common으로 과도하게 올리지 않는다.
- **동작 불변·영향 범위:** 통합으로 동작/렌더 결과가 달라지면 안 된다(「style·로직 불변」). 광역 영향(공용 컴포넌트·formatter류 등)이 우려되면 사용처를 전수 확인해 영향 범위를 정리하고 **먼저 컨펌을 받은 뒤** 실행한다. 리포트에 **무엇을 → 어디로 통합/추출했는지** 명시한다.

### type 분리 (정배 + 중복 타입 묶음)

- **정배:** `features/{feature}/components/{Component}/`는 `index.tsx` + `type.ts`로 구성하고, 스타일이 필요하면 `style.ts`를 더한다. 그 컴포넌트의 props·로컬 타입은 `type.ts`에 두고, `index.tsx`에서는 `import * as T from "./type"` 형태로 사용한다.
- **빈 style 파일 금지:** 따로 스타일을 입힐 필요가 없으면 `style.ts`는 생략한다. `export {}`만 있는 빈 style 파일은 만들지 않는다.
- **디렉토리 깊이 2단계 제한:** `components/` 아래 디렉토리는 **두 단계까지만** 둔다. `components/{Component}/`(1단계)와 `components/{Component}/{Sub}/`(2단계)는 허용하지만, 그 아래 또 디렉토리를 파는 3단계 중첩(`components/{Component}/{Sub}/{SubSub}/`)은 만들지 않는다. **모든 컴포넌트는 `디렉토리/index.tsx` 구조이며 `{SubSub}.tsx` 같은 단독 파일은 두지 않는다.** 따라서 3단계가 될 하위 컴포넌트(손자)는 2단계 디렉토리 안에 파일로 두는 게 아니라, **최상위 컴포넌트의 직속 sub(`components/{Component}/{SubSub}/index.tsx`)로 평탄화**하거나, 사소하면 inline 유지한다. type/constants/utils 분리 기준은 컴포넌트가 중첩돼 있어도 동일하게 적용하되, 디렉토리 깊이만 2단계로 제한한다. **깊이를 늘리는 것은 분량·복잡도가 정당화할 때만**이며, 양이 적으면 굳이 깊게 파지 않는다.
- **중복 타입 묶음:** 하위 컴포넌트들(중첩 포함)에서 여러 번 중복되는 타입은 `features/{feature}/types/` 디렉토리에 **용도별 `.ts` 파일**(용도/로직이 같은 타입끼리 묶음)로 분리해 재사용한다.
- 단일 컴포넌트 전용 타입을 `types/`로 올리지 않는다. 반대로 여러 컴포넌트가 공유하는 타입을 각 `type.ts`에 중복 정의하지 않는다.

### 단독 사용 컴포넌트 재배치 (디렉토리 2단계 제한)

- `components/` 아래 디렉토리는 **두 단계까지만** 둔다(`{Component}/{Sub}/`까지 허용, `{Component}/{Sub}/{SubSub}/` 3단계 금지).
- 사용처가 1곳이면 루트 `components`에 방치하지 말고 실제 사용하는 부모 컴포넌트 디렉토리 하위로 옮긴다. 단 이 이동이 3단계를 만든다면 디렉토리를 더 파거나 파일로 두지 말고, **최상위 컴포넌트의 직속 sub(`{Component}/{SubSub}/index.tsx`)로 평탄화**(사소하면 inline)한다.
- 사용처가 2곳 이상이면 **가장 가까운 공통 조상** 하위(2단계 한도 내)로 옮긴다. 서로 다른 라우트(페이지)에 걸치면 common으로 승격(「constants/utils 위치」 준용).

### 훅 추출 (다중 호출·파생 가공·브라우저 통신 로직)

- 컴포넌트 본문에 흩어진 아래 성격의 로직은 **효과적이라 판단될 때** 커스텀 훅(`features/{feature}/hooks/` · 여러 라우트 공유 시 `features/common/hooks` 또는 `src/hooks`, 「constants/utils 위치」 준용)으로 묶는다. **목적은 안정적 로딩·가독성·재사용**이지 훅 갯수 늘리기가 아니다.
- **다중 API 호출 → queries로 취합:** 한 컴포넌트에서 여러 비동기 호출을 따로 받아 `isLoading`/`error`를 수동 조합하던 부분은, 쓰는 데이터 패칭 라이브러리의 **묶음 API(예: TanStack Query `useQueries`)**로 취합해 로딩·에러를 한 번에 안정적으로 다룬다. 호출 개수·키·옵션은 기존과 동일하게 유지한다(동작 불변).
- **다중/대량 data formatting → 훅으로:** 호출 후 포매팅·정규화·집계를 **여러 건 또는 대량으로** 처리하는 파생 가공이 컴포넌트 본문을 가리면 훅으로 묶는다. 순수 변환 함수 자체는 `utils/`(「constants/utils 위치」)에 두고, **훅은 그 util들을 조합해 메모이즈된 결과를 돌려주는 역할**로 한다(`useMemo` 의존성은 기존 계산 입력과 동일하게).
- **브라우저 창과 통신하는 로직 → 훅으로:** `window.resize`(화면 크기 감지), `scroll`(스크롤 위치 추적), 다크모드 설정, 네트워크 연결 상태(online/offline) 등 **브라우저 API와 통신하는 effect**는 전용 훅(`useWindowSize`, `useScrollPosition`, `useDarkMode`, `useOnlineStatus` 등)으로 묶는다. 같은 성격 로직이 이미 여러 곳에 복붙돼 있으면 공용 훅으로 통합(「중복·반복 통합」).
- **side effect·로직 불변 점검(필수):** 훅 추출은 가장 사이드이펙트가 큰 작업이다. 옮기기 전후로 반드시 점검한다 —
  - **이벤트 등록/해제 대칭:** `addEventListener`↔`removeEventListener`, 구독↔구독해제, 타이머 `set`↔`clear`가 cleanup에서 빠짐없이 짝맞는지.
  - **effect 의존성·실행 타이밍 동일:** deps 배열, 실행/재실행 시점, 초기값, SSR/마운트 가드(`typeof window` 등)가 기존과 같은지. 호출 순서·조건부 호출로 **훅 규칙(Rules of Hooks)**을 깨지 않는지.
  - **참조 안정성:** 반환 함수/객체가 매 렌더 새로 생겨 하위 재렌더나 effect 재실행을 유발하지 않는지(`useCallback`/`useMemo`로 기존 동작과 동일하게).
  - **로직 변경 0:** 추출은 **이동·캡슐화일 뿐 동작이 달라지면 안 된다**(「style·로직 불변」). 값/타이밍/렌더 결과가 1도 달라지지 않는지 확인하고, 애매하면 추출하지 말고 **먼저 컨펌**받는다.
- 리포트에 **무엇을 어떤 훅으로 묶었는지 / 점검한 side effect 항목**을 명시한다.

### case 분기는 props로 관리

- 컴포넌트가 case별로 다르게 동작·표시돼야 하는 부분은 props 추가 또는 **optional prop**으로 분기 관리한다. optional prop의 기본값을 기존 동작과 동일하게 두어 **기존 호출부 동작은 불변**으로 유지한다.
- 분기·흐름이 복잡하면 흐름 파악용 주석을 함께 단다(「주석 규칙」).

### 컴포넌트 이름 유일성 (도메인 접두사)

- 컴포넌트 이름은 프로젝트 안에서 **겹치지 않게 unique**하게 짓는다. 내용이 미묘하게 달라 분리해 둔 컴포넌트가 같은 이름을 갖지 않도록 한다.
- 도메인/용도에 따라 달라지는 경우 **도메인을 접두사로** 붙인다. 어느 컴포넌트의 하위로 들어가 있든 동일하게 적용한다.
  - 예) 벨트의 R&D 탭 → `BeltRndTab`, 특화단지의 R&D 탭 → `SpecializationRndTab` (둘 다 `RndTab`으로 두지 않는다)
- 이름을 바꾸면 파일·디렉토리명, import 경로, 사용처를 모두 함께 갱신한다(「import 경로 정리」).

### 주석 규칙

- **import문 위 설명 주석은 추가하지 않는다.**
- **컴포넌트 목적 주석:** 각 컴포넌트는 **선언부 바로 위**(import문 위가 아님)에 "**무엇을 그리는 컴포넌트인가**"를 한 줄로 단다. 예) `export default function ...` 위에 `// 국가별 R&D 총액 비교 카드`.
- **util·헬퍼 함수 주석:** 정의 바로 위에 "**어떤 경우에 쓰는지**" 짧은 용도 주석을 단다.
- **JSX 렌더 위치 주석:** return부에서 imported 컴포넌트를 렌더링하는 위치에 어떤 컴포넌트인지 알 수 있는 JSX 주석을 단다.
  - **블록 시작 위 한 곳에만:** "이 블록이 무엇을 렌더하는가"는 그 블록(조건부 삼항 포함) **시작 바로 위 한 줄**에 단다. 삼항 분기 안쪽이나 래퍼 내부에 같은 의미의 주석을 중복으로 달지 않는다.
  - **주석 때문에 fragment로 감싸지 않는다:** 단일 자식을 주석 달려고 `<>…</>`로 감싸지 말고, 주석을 블록 위로 올린 뒤 자식을 그대로 렌더한다.
    ```tsx
    // ❌ fragment로 감싸고 안쪽에 주석
    {cond ? <Loading /> : empty ? <Empty /> : (
      <>
        {/* 주요국 수입의존도 차트 */}
        <SupplyRiskChart rows={rows} />
      </>
    )}

    // ✅ 주석은 블록 위 한 줄, 단일 자식은 그대로
    {/* 주요국 수입의존도 차트 */}
    {cond ? <Loading /> : empty ? <Empty /> : <SupplyRiskChart rows={rows} />}
    ```
- **단계 주석:** 로직·구조가 복잡하면 흐름을 파악하기 쉽도록 중간중간 단계 주석을 단다.

### 안티패턴 점검 (리포트 전용 — 자동수정 안 함)

- 전수조사 시 아래 안티패턴을 함께 스캔한다. **처리 정책: 발견하면 리포트만 한다.** "안티패턴이 맞는지 / 동작이 보존되는 안전한 수정인지"를 스킬이 확신하기 어려우므로 **이 스킬에서는 직접 고치지 않는다.** 고칠지 여부·방법은 리포트를 보고 사용자가 판단한다(「style·로직 불변」 절대 우선).
- **다른 기준의 분리·이동 작업과 구분:** inline/섹션 분리·중복 통합·훅 추출처럼 **이 스킬이 수행 대상으로 명시한 구조 변경**은 그대로 진행한다. 이 기준은 그 외 "**고치려면 동작·로직에 손대야 하는** 안티패턴"을 **수정 없이 짚어만 주는** 역할이다.
- **lint와 역할 분담:** ESLint로 강제 가능한 항목(`react-hooks/rules-of-hooks`·`exhaustive-deps`, `no-unused-vars`, `@typescript-eslint/no-explicit-any` 등)은 **규칙에 맡기고**, 이 스킬은 lint가 못 잡는 **의미·구조적 안티패턴**에 집중한다. lint로 막는 게 더 나은 항목을 발견하면 규칙 활성화를 **제안**한다(직접 설정 변경은 하지 않음).
- **스캔 대상 (모두 리포트만):**
  - **React 상태/렌더:** 파생 가능한 값을 `useState`+`useEffect`로 동기화(파생 state), props를 `useState` 초기값으로 복사 후 미동기화(stale state), 렌더 중 `setState`·부수효과·뮤테이션, 재정렬/삽입·삭제 리스트의 array index `key`, 성능 민감 경로의 인라인 객체/배열/함수 props로 `memo` 무력화.
  - **훅:** 조건부/반복문 안 훅 호출, `useEffect` 의존성 누락·과다, cleanup 누락(이벤트/타이머/구독), 이벤트 핸들러로 충분한 걸 `useEffect`로 대체, effect 내부 직접 `async`로 응답 순서 경합(race) 미처리.
  - **비동기/데이터:** 로딩·에러 처리 누락, 응답 순서 보장 없는 패칭, 취소되지 않는 요청.
  - **TypeScript:** `any` 남용, 불필요한 `as` 단언·non-null `!` 남용(타입 가드로 대체 가능), `==`/`!=`.
  - **일반:** 사용 안 하는 import/변수, 도달 불가 dead code, 잔존 `console.log`/디버그 코드, 반복되는 매직 넘버·문자열.
- **확장:** 프로젝트별로 자주 나오는 안티패턴은 이 목록에 항목을 덧붙여 관리한다. 항목은 "무엇 / 왜 위험 / 권장 방향" 형식을 유지한다(수정은 여전히 리포트만).
- 발견 항목은 「리포트」의 안티패턴 슬롯에 정리하되, **직접 수정은 하지 않는다.** 사용자가 개별로 수정을 지시하면 그때 동작 영향을 확인하고 진행한다.

## 진행 절차 (어떻게 진행하나)

1. **전수조사** — 대상 폴더를 하위까지 전부 훑어 위 정리 기준별 후보를 수집한다(구조 분리·중복/반복·훅 후보·안티패턴).
2. **제안 후 수정** — 전수조사 결과·수정안을 먼저 제시하고, 합의 범위로 수정한다("검토만"이면 여기서 멈춤).
3. **재전수검사** — 작업 후 다시 전수검사한다.
   - 누락된 inline props, inline tooltip content, inline helper component, 중복 constants/utils, 중복 컴포넌트·스타일 블록·로직(훅/함수), 단독 사용 컴포넌트가 없는지(「중복·반복 통합」).
   - **JSX 반환 map 재검사(필수):** 모든 `.map(` 호출을 콜백 끝(return)까지 트레이스해 JSX 반환 항목이 분리됐는지(또는 inline 허용 예외에 정확히 해당하는지) 다시 확인한다. 특히 `=> {` block-body + 지연 return 형태는 1차에서 묻히므로 반드시 재확인한다(「inline 분리」).
   - **훅 추출 side effect 재검사(필수):** cleanup 대칭, effect 의존성·실행 타이밍, 참조 안정성, 훅 규칙 위반 여부를 다시 점검해 **동작이 추출 전과 동일한지** 확인한다(「훅 추출」).
   - **안티패턴 재검사:** 스캔 목록을 다시 훑어 누락이 없는지 확인하고 리포트에 정리한다(직접 수정하지 않는다).
4. **import 경로 정리** — 파일 이동/구조 변경이 있으면 import 경로를 모두 정리한다. barrel(`index.ts`) re-export와 `@/` alias 경로까지 갱신한다.
5. **검증** — 동작 불변을 확인한다. **타입 통과 ≠ 동작 동일**임에 유의한다.
   - **타입체크:** 패키지 매니저를 고정하지 않는다(레거시 프로젝트도 대상). 매니저는 lockfile/설정으로 감지한다 — `pnpm-lock.yaml`→`pnpm`, `yarn.lock`→`yarn`, `package-lock.json`→`npm`, `bun.lockb`→`bun`. `package.json`의 `packageManager` 필드가 있으면 우선한다. 감지한 매니저로 `<pm> run typecheck`를 돌리고, `typecheck` 스크립트가 없으면 `<pm> exec tsc --noEmit`(npm은 `npx tsc --noEmit`)로 대체한다.
   - **테스트:** 변경 범위에 관련 테스트가 있으면 실행한다. 없으면 "테스트 없음 → 동작 보장 약함"을 리포트에 명시한다.
   - **빌드/lint:** 가능하면 빌드 또는 lint 통과를 함께 확인한다.
   - **동작 위험 큰 변경의 게이트:** 훅 추출·중복 통합 등 동작이 바뀔 위험이 큰 변경은 테스트로 못 덮으면 **수동 동작 확인 또는 사용자 컨펌**으로 마무리한다. 애매하면 수정하지 말고 컨펌받는다.
6. **리포트** — 아래 「리포트」 형식으로 보고한다.

---

## 리포트 (출력 형식)

작업 후 아래 슬롯으로 보고한다. 해당 없는 슬롯은 "해당 없음"으로 명시한다.

1. **전수조사 결과** — 현재 파일 / 문제 / 옮길 위치 / 도메인 vs common 판단 근거 / 스타일·로직 영향 / 우선순위.
2. **수정 내역** — 변경 파일 묶음과 **무엇을 → 어디로 / 어떻게 변경**했는지. 특히 옮기거나 시그니처를 바꾼 constants/utils, 통합·추출한 중복 컴포넌트·스타일·로직·훅을 명시한다.
3. **안티패턴 리포트** — 발견한 안티패턴 / 위치 / 왜 위험한지 / 권장 수정 방향. **직접 수정하지 않았음**을 함께 표시한다(lint로 막는 게 나은 항목은 규칙 활성화 제안).
4. **검증 결과** — 타입체크 / 테스트(없으면 그 사실) / 빌드·lint 결과.
5. **컨펌 필요 · 남은 리스크** — 광역 공용 util·공용 컴포넌트 변경 등 사전 컨펌이 필요한 항목, 동작 보장이 약한 부분.

## 금지

- import문 위 설명 주석 추가
- style 변경 / 「style·로직 불변」 예외를 벗어난 로직 변경
- 단독 사용 leaf 컴포넌트를 상위 공용 폴더에 방치
- 재사용성 없고 의미 없는 사소한 조각까지 강제 분리(과분리로 가독성 저해)
- `components/` 아래 3단계 이상 중첩 디렉토리 생성(2단계까지만 허용)
- 미묘하게 다른 컴포넌트에 동일한 이름 사용(도메인 접두사로 구분하지 않음)
- 단일 페이지 전용 코드를 common으로 과도하게 승격
- 의미·동작이 다른 컴포넌트·로직을 겉모습만 비슷하다고 억지로 통합(분기 지옥·가독성 저해)
- 동일 styled 블록을 여러 `style.ts`에 중복 선언 방치(사용 범위에 맞는 한 곳으로 통합하지 않음)
- 중복 컴포넌트·로직 통합 시 동작/렌더 결과를 바꾸거나, 광역 영향을 영향 범위 컨펌 없이 통합·추출
- 광역 공용 util(예: formatter)을 영향 범위 컨펌 없이 이동·시그니처 변경
- 훅 추출 시 이벤트/구독/타이머 cleanup 누락, effect 의존성·실행 타이밍·참조 안정성 변경(동작 변화)
- 동작 불변 보장이 애매한데 컨펌 없이 훅 추출·중복 통합 강행
- 안티패턴을 스킬이 직접 수정(리포트만 — 수정은 사용자 지시 후)
- lint로 강제 가능한 항목을 스킬에서 임의로 settings/eslint 설정 변경(제안만 한다)
- 반복되는 동일 구조 묶음(헤더/타이틀 등)을 "사소하다"는 이유로 분리하지 않고 여러 곳에 중복 방치
- 주석을 달기 위한 불필요한 `<>…</>` 래핑, 조건부 분기·래퍼 안 렌더 주석 중복
- 검증을 타입체크만으로 끝내고 동작 위험 큰 변경을 컨펌·확인 없이 마무리
- 전수조사했다고 말하고 일부 디렉토리만 확인하는 것

## 완료 조건

> 아래는 **대상이 있을 때**의 완료 기준이다. 이번 범위에 해당 대상이 없는 항목은 "N/A"로 명시한다.

- 분리한 컴포넌트의 props type은 모두 `type.ts`로 분리(사소해서 inline 유지한 것은 제외)
- 분리가 필요한(반복·복잡) inline tooltip content 0건 — 사소한 1회성 tooltip content는 inline 유지 가능
- JSX를 반환하는 모든 `.map(` 항목이 분리됨(또는 inline 허용 예외에 정확히 해당) — 부모 return부에 펼쳐진 채 잔존 0건. 화살표 직후 반환·block-body(중간 변수+지연 return) **둘 다** 점검 완료
- 한 파일에 여러 섹션이 펼쳐진 채 잔존 0건 — 섹션 컴포넌트로 분리, 섹션 간 반복 스타일은 부모 `style.ts`에 선언하고 하위가 import해 사용(중복 선언 0건)
- 2회 이상 반복되는 구조 묶음(헤더/타이틀 등) 공통 컴포넌트화 완료(중복 마크업 0건), 해당 공통 스타일은 단일 위치 선언
- 주석용 `<>…</>` 래핑 0건, 렌더 주석은 블록당 위 한 곳(분기·래퍼 안 중복 0건)
- 흐름을 가리는 내부 helper component 잔존 0건 — 사소한 것은 inline 유지 가능
- 단독 사용 컴포넌트 루트 방치 0건
- 컴포넌트 이름 유일성 확보(미묘하게 다른데 같은 이름 0건, 필요 시 도메인 접두사)
- 컴포넌트 `type.ts` 분리 및 `T.*` import 적용, 중복 타입은 `features/{feature}/types/` 용도별 묶음으로 정리
- 스타일 불필요 시 `style.ts` 생략(빈 `export {}` style 파일 0건)
- 중복 constants/utils 정리 완료(도메인/common 기준 적용)
- 중복 컴포넌트·스타일 블록·로직(훅/함수) 통합 완료(의미·구조·동작 동일한 것만, 도메인/common 배치 적용) — 무의미한 반복 0건
- 다중 API 호출은 queries 묶음으로 취합, 다중/대량 파생 가공·브라우저 통신(resize/scroll/다크모드/네트워크) effect는 훅으로 분리 — side effect(cleanup 대칭·의존성·실행 타이밍·참조 안정성) 점검 완료, 동작 불변
- 안티패턴 스캔 완료 — **리포트만**(직접 수정 0건), 위치·위험·권장 방향 정리, lint 강제 가능 항목은 규칙 제안
- 컴포넌트 목적 주석 + return부 JSX 렌더 주석 적용, import 위 주석 0건
- (수정한 경우) 검증 통과 — 타입체크 + 테스트/빌드(있으면), 동작 위험 큰 변경은 확인·컨펌 완료
