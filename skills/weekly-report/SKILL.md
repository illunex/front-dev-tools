# weekly-report

전주에 작성한 차주 계획을 기준 목록으로 삼고, 이번 주(또는 특정 주)의 GitHub 커밋과 기간 내 merge된 내가 연 PR을 대조해 **프로젝트 → 큰 업무 → 중간 업무 → 상세 업무** 3단계 주간보고로 정리합니다.

## 사용 시점

다음과 같은 요청이 왔을 때 이 skill을 사용합니다:

- "주간보고 정리해줘" / "주간 작업 내역 뽑아줘"
- "이번주 커밋 정리해줘" / "이번주에 뭐 했는지 보여줘"
- "지난주 작업 내역" / "저번주 커밋 요약"
- "weekly report" / "weekly summary"
- "주간보고 표로 만들어줘" / "주간보고 테이블 만들어줘" / "주간보고 html로" → Step 13의 HTML 표 산출물로 응답

## 출력 포맷

```
[프로젝트 타이틀]
- 큰 업무명 ~M/D nn%
  ◦ 중간 업무명 nn%
    : 상세 내용 nn%
    : 상세 내용 nn%
  ◦ 중간 업무명 nn%
    : 상세 내용 nn%

[다른 프로젝트 타이틀]
- 큰 업무명 ~M/D nn%
  ◦ 중간 업무명 nn%
    : 상세 내용 nn%
```

- 1단계 `[프로젝트 타이틀]`: 레포 이름이 아니라 HTML head 타이틀. CLI가 조회한 값을 그대로 사용
- 2단계 `- 큰 업무명 ~M/D nn%`: 고정 어휘 7종 중 하나, 들여쓰기 없음
- 3단계 `  ◦ 중간 업무명 nn%`: 공백 2칸 + `◦ `
- 4단계 `    : 상세 내용 nn%`: 공백 4칸 + `: `
- **진행률(`nn%`)은 큰·중간·상세 세 단계 모든 줄에 표시한다.**
- **날짜(`~M/D`)는 큰 업무 줄에만 표시한다.** 중간·상세 줄에는 날짜를 쓰지 않음
- 기간 기본값: 요청 시점을 포함하는 ISO 주(월~일)
- 완료로 판단되는 항목만 `100%`로 표시하고, 완료 근거가 부족하면 10% 단위의 `100%` 미만 진행률로, 미착수 항목은 `0%`로 표시
- 문구·라벨 수정 같은 사소한 변경은 업무 범위에 넣지 않음
- merge / revert 커밋은 자동 제외
- 날짜는 항목 상태에 따른 완료일·예상 종료일·작업일 중 하나를 반드시 표시하며 생략하지 않음

## 계정 간 표기 일관성 원칙

같은 프로젝트를 여러 명이 각자 작성해도 표기가 충돌하지 않도록, 아래를 **작성자 재량이 아닌 고정 규칙**으로 취급합니다.

1. 프로젝트명은 CLI가 조회한 HTML head 타이틀을 그대로 쓰고, 임의로 줄이거나 번역하거나 레포명으로 바꾸지 않습니다.
2. 큰 업무는 아래 고정 어휘 7종 밖으로 나가지 않습니다. 새 어휘를 만들지 않고 가장 가까운 어휘로 흡수합니다.
3. 중간 업무의 묶음 단위는 CLI `영역:` 값입니다. 같은 영역은 항상 같은 중간 업무명으로 씁니다.
4. 상세 업무는 CLI `파일:`·`신호:`에서 확인되는 작업만 적고, 확인할 수 없는 작업을 지어내지 않습니다.
5. 홍보성 수식어(원활하게, 대폭, 깔끔하게)와 창작 표현을 넣지 않습니다. 명사형 사실만 적습니다.
6. 정렬은 아래 정렬 규칙을 그대로 따릅니다. 중요도 판단으로 순서를 바꾸지 않습니다.

## Prerequisites

1. **Bash 실행 환경** — macOS/Linux 터미널 또는 Windows Git Bash/WSL
2. **GitHub CLI(`gh`) 설치** — macOS는 `brew install gh`, Windows는 `winget install GitHub.cli` 또는 [cli.github.com](https://cli.github.com)
3. **gh 인증** — `gh auth login` 완료
4. **jq 설치** — macOS는 `brew install jq`, Windows는 `winget install jqlang.jq` 또는 [jq 다운로드](https://jqlang.github.io/jq/download/)

## Step 1: weekly-report CLI 설치 확인

```bash
command -v weekly-report
```

CLI가 없으면 **사용자에게 다음 설치 명령을 제안하고 동의를 받은 뒤 실행**합니다:

```bash
curl -fsSL https://raw.githubusercontent.com/illunex/front-dev-tools/main/install/install-weekly-report.sh | bash
```

설치 경로는 기본적으로 `~/.local/bin/weekly-report`입니다. 설치 후 `~/.local/bin`이 `PATH`에 없다면 셸 프로필에 아래 줄을 추가해야 합니다:

```bash
export PATH="$HOME/.local/bin:$PATH"
```

## Step 2: 전주 차주 계획을 기준 목록으로 구성

사용자가 전주에 작성한 금주 할 일 또는 `[차주 주간보고]`를 제공하면 다음 순서로 처리합니다.

1. 전주 계획의 모든 항목에서 업무명, 예상 종료일, 전주 진행률, 사유를 추출해 순서를 유지합니다.
2. 전주 계획의 모든 항목을 금주 보고의 기준 목록에 먼저 넣습니다. 금주 커밋이 없다는 이유로 항목을 제외하지 않습니다.
3. 금주 커밋·PR 제목과 변경 맥락을 업무 단위로 비교해 관련 계획 항목에 연결합니다. 문구가 정확히 일치할 때만 연결하지 말고 기능·화면·도메인 맥락을 함께 사용합니다.
4. 계획에 없던 금주 작업은 별도 신규 항목으로 추가합니다.
5. 하나의 커밋이 여러 계획 항목의 근거가 될 수 있지만, 각 항목의 완료 범위가 확인될 때만 진행률에 반영합니다.
6. 연결 근거가 불명확한 항목은 전주 진행률을 임의로 올리거나 완료 처리하지 않습니다.

전주 계획이 대화나 입력에 없으면 자동으로 저장된 것으로 가정하지 않습니다. 먼저 사용자에게 전주에 작성한 차주 계획을 요청하고, 사용자가 없다고 확인한 경우에만 커밋 기준으로 보고를 생성합니다.

### 구 포맷 전주 계획 이관

전주 계획이 `- 업무명 ~M/D nn%` 평면 포맷이면 다음과 같이 계층형으로 옮깁니다.

1. 전주 업무명을 고정 어휘 중 가장 가까운 **큰 업무**에 배정합니다.
2. 전주 업무명 자체는 버리지 않고 해당 큰 업무 아래의 **중간 업무** 또는 **상세 업무**로 내립니다.
3. 전주 진행률과 예상 종료일은 배정된 큰 업무 줄의 값으로 승계합니다.
4. 서로 다른 전주 항목이 같은 큰 업무로 모이면 진행률은 각 항목의 가중 없는 평균이 아니라 **가장 낮은 항목 기준**으로 잡고, 근거는 `[미완료 판단 근거]`에 적습니다.

## Step 3: 인자 추론

사용자 요청에서 다음 인자를 추론합니다:

| 인자 | 추론 방법 | 기본값 |
| --- | --- | --- |
| `--week <n>` | "지난주" → `1`, "이번주" → `0` | `0` |
| `--from`, `--to` | 특정 날짜를 명시한 경우 사용 | 자동 계산(ISO week) |
| `--author <login>` | 다른 사람의 내역 요청 시 지정 | 인증된 사용자 |
| `--limit <n>` | 직접 커밋 또는 merge된 PR이 많을 것으로 예상될 때 조정 | `200` |
| `--no-files` | 변경 파일 조회를 생략할 때만 지정. 기본은 조회함 | 미지정 |

변경 파일 조회는 기본으로 켜 둡니다. 중간·상세 업무와 큰 업무 분류가 모두 변경 경로에 근거하기 때문에, 사용자가 속도를 이유로 요청하지 않는 한 `--no-files`를 붙이지 않습니다.

## Step 4: 실행

```bash
# 이번 주 (기본)
weekly-report

# 지난주
weekly-report --week 1

# 특정 날짜 범위
weekly-report --from 2026-04-13 --to 2026-04-19

# 다른 사용자
weekly-report --author octocat
```

CLI는 직접 커밋 검색 결과와, 같은 기간에 merge된 `--author` 사용자의 PR에 포함된 커밋을 함께 수집합니다.

## Step 5: CLI 수집 결과 해석

CLI 출력은 최종 보고서가 아니라 **수집 결과**입니다. 사용자에게 그대로 보여주지 않습니다.

```
# weekly-report 수집 결과 (2026-09-14 ~ 2026-09-20 / octocat)

[Stock Link] (illunex/stock-link-mobile)
- feat: 종목 상세 차트 영역 퍼블리싱 ~9/10
  영역: stock/detail
  신호: 퍼블리싱
  파일: src/pages/stock/detail/Chart.module.scss, src/pages/stock/detail/Chart.tsx
```

| 줄 | 의미 | 사용처 |
| --- | --- | --- |
| `[타이틀] (owner/repo)` | HTML head 타이틀과 원본 레포 | 1단계 프로젝트명. 최종 출력에는 `(owner/repo)`를 쓰지 않음 |
| `- subject ~M/D` | 커밋 subject와 작업일 | 상세 업무 근거, 날짜 계산 |
| `영역:` | 라우트·feature 경로에서 뽑은 화면 영역 | 중간 업무 묶음 단위 |
| `신호:` | 변경 경로에서 뽑은 작업 성격 | 큰 업무 분류 근거 |
| `파일:` | 변경 파일 경로 | 상세 업무 판단 근거 |

- 타이틀이 레포명과 같게 나왔다면 CLI가 head 타이틀을 찾지 못한 경우입니다. 이때만 사용자에게 프로젝트 정식 명칭을 물어봅니다.
- `영역: 기타`만 있는 커밋은 문서·설정 변경일 가능성이 높으므로 화면 단위로 올리지 않습니다.

### 조회 범위 한계

CLI는 로컬 git이 아니라 GitHub 원격 서버를 검색하므로 push하지 않은 로컬 커밋은 절대 집계되지 않습니다. 여기에 더해 다음 두 조회 방식 각각의 범위 제한이 있습니다.

- `gh search commits`는 레포의 **default 브랜치**에 있는 커밋만 검색합니다.
- `gh search prs --merged`는 그 기간에 **merge된 PR**의 포함 커밋만 잡습니다.
- 따라서 **push는 했지만 default 브랜치도 아니고 merge된 PR도 없는 feature 브랜치 커밋**(예: 리뷰 대기 중인 PR)은 두 경로 어디에도 잡히지 않아 누락됩니다. 보고를 확정하기 전에 사용자에게 "현재 리뷰 대기 중이거나 아직 merge되지 않은 PR이 있는지" 한 번 확인합니다.

### 대안: 여러 사람의 완료 목록을 직접 받은 경우

팀 전체를 취합할 때는 CLI 대신, 각자 이미 날짜·진행률까지 정리한 평면 목록을 사용자가 그대로 붙여넣기도 합니다.

```text
이름
[프로젝트명]
- 항목 설명 ~M/D nn%
- 항목 설명 ~M/D nn%

다른 이름
[프로젝트명]
- 항목 설명 ~M/D nn%
```

이 경우 Step 1(CLI 실행)~Step 5(수집 결과 해석)를 건너뛰고, 붙여넣은 텍스트를 그대로 수집 결과로 취급해 Step 6부터 이어갑니다.

- **날짜·진행률은 사용자가 이미 확정한 값을 그대로 씁니다.** 완료로 명시된 항목(`100%`)을 임의로 낮추지 않습니다. 진행률을 적지 않은 항목만 Step 8의 추정 기준을 적용합니다.
- 큰 업무 분류(Step 6)는 CLI `신호:` 대신 **항목 문구 자체의 키워드**로 판단합니다: 퍼블·디자인·레이아웃·반응형 → `퍼블리싱`, 신규 연동 문구(신규 연동일 때만) → `API 연결`, 오류·버그·문제 수정 → `버그 수정`, 변경·요청·명칭 변경 → `변경 반영`, 리팩토링·구조 개선 → `리팩토링/구조 개선`, 배포·환경·CI → `배포/환경 설정`, 그 외 → `기능개발`.
- 같은 프로젝트를 여러 사람이 각자 적어도 **사람별로 별도 행·블록을 유지**합니다. 사람을 합쳐서 요약하지 않습니다.
- 프로젝트명 표기가 사람마다 다르면(`Em-graph`/`em-graph`, `삼성증권 m pop`/`삼성증권 mPop`) Step 4의 표기 일관성 원칙에 따라 하나로 통일합니다.
- Step 13 표로 출력할 때 이 사람 구분이 그대로 "담당자" 열이 됩니다.

## Step 6: 큰 업무 분류

큰 업무는 아래 **고정 어휘 7종**만 사용합니다.

| 큰 업무 | 범위 |
| --- | --- |
| `퍼블리싱` | 마크업, 스타일, 반응형, 에셋 적용 등 화면 구현 |
| `API 연결` | **신규 연동**(새 엔드포인트 최초 연결) 착수·완료 |
| `기능개발` | 화면 로직, 상태 관리, 유효성 검사 등 동작 구현 |
| `버그 수정` | 기존 동작 오류·예외·장애 대응 |
| `리팩토링/구조 개선` | 동작 변화 없는 구조 정리, 공통화, 타입 정리 |
| `배포/환경 설정` | CI, 빌드, 환경 변수, 의존성, 배포 설정 |
| `변경 반영` | 기획 변경, 디자인 변경, 추가 요청, 피드백 반영 |

분류는 아래 순서로 **처음 걸리는 항목에서 확정**합니다. 순서를 바꾸지 않습니다.

1. `신호:`가 `배포/환경 설정`만으로 구성 → `배포/환경 설정`
2. 기존 동작 오류 수정 근거(`fix`, `hotfix`, 오류, 예외, 장애) → `버그 수정`
3. 기획·디자인·요청 변경 반영 근거(변경 반영, 추가 요청, 수정 요청, 피드백, 디자인 변경, 기획 변경) → `변경 반영`
4. 동작 변화 없는 구조 정리 근거(`refactor`, `chore`, 분리, 공통화, 타입 정리) → `리팩토링/구조 개선`
5. `신호:`에 `API 연결` 포함되고 **새 엔드포인트를 처음 연결하는 작업**일 때만 → `API 연결`
6. `신호:`가 `퍼블리싱`만으로 구성되거나, 커밋 접두사가 `style:`이거나, 마크업·레이아웃·반응형·디자인 토큰 변경이 주된 근거 → `퍼블리싱`
7. 그 외 전부 → `기능개발`

- 한 커밋이 여러 성격을 가지면 위 순서에서 먼저 걸리는 하나에만 배정하고, 다른 성격은 상세 업무 문장으로 표현합니다.
- 같은 프로젝트 안에서 같은 큰 업무는 하나의 줄로 합칩니다. `퍼블리싱` 줄을 두 개 만들지 않습니다.
- Tailwind나 CSS-in-JS 프로젝트는 스타일 파일이 없어 `신호:`에 `퍼블리싱`이 잡히지 않습니다. 6번의 보조 근거(`style:` 접두사, 마크업·반응형·토큰 변경)로 판정하고, 신호가 없다는 이유로 퍼블리싱 작업을 `기능개발`에 묻지 않습니다.
- `test:` 커밋은 단독 큰 업무로 만들지 않고, 검증 대상 업무의 상세 업무 한 줄로 합칩니다.
- **`API 연결`은 신규 연동일 때만 씁니다.** 이미 연결된 API의 응답 예외 처리, 요청 파라미터 정리, 로딩·에러 상태 보강처럼 기존 연동에 딸린 작업은 `기능개발`로 합치고, 상세 업무 문장을 `OO API 연결 및 OO 기능 구현`처럼 API 연동과 기능 구현을 한 문장에 표현합니다. `API 연결` 큰 업무 줄을 별도로 만들지 않습니다.

## Step 7: 중간 업무와 상세 업무 작성

### 중간 업무

- 형식: `<화면 타이틀> 페이지`
- 묶음 단위는 CLI `영역:` 값입니다. 같은 영역의 커밋은 같은 중간 업무로 모읍니다.
- 화면 타이틀은 다음 순서로 정합니다.
  1. 해당 화면 코드의 메타 타이틀 또는 라우트 정의에 적힌 화면명
  2. 화면 상단 제목(헤더, `h1`)에 쓰인 문구
  3. 라우트 경로를 업무 용어로 그대로 옮긴 이름 (`stock/detail` → `종목 상세`)
- 같은 이름의 화면이 둘 이상이면 `종목 상세 페이지(stock/detail)`처럼 괄호에 경로를 덧붙여 구분합니다.
- 위젯·시트·섹션처럼 한 화면의 부분 영역은 별도 중간 업무로 만들지 않고 그 화면의 중간 업무로 합칩니다. (`keyword-filter-sheet`, `keyword-view-sheet` → `키워드 관계망 페이지`)
- 화면이 아닌 기능 모듈 영역(`auth`, `social-report`처럼 store·types·utils만 있는 영역)은 `페이지`를 붙이지 않고 `인증 모듈`, `에러 로그 수집 모듈`처럼 `<대상> 모듈`로 씁니다.
- `영역:`이 `공통/...`이면 화면이 아니므로 `페이지`를 붙이지 않고 `공통 컴포넌트`, `공통 스타일`, `공통 API 모듈`, `공통 프로바이더`, `전역 상태`처럼 대상 이름을 씁니다.
- `영역:`이 `기타`이면 `프로젝트 설정`, `배포 파이프라인`, `문서`처럼 대상 이름을 씁니다.

### 상세 업무

- 커밋 하나를 그대로 한 줄로 옮기지 않습니다. 같은 성격의 커밋을 묶어 **중간 단위 작업**으로 적습니다.
- 한 중간 업무당 상세는 2~5줄을 기준으로 합니다.
- **보고 가치가 없는 사소한 변경은 상세 업무로 올리지 않고 생략합니다.** 문구·라벨·타이틀 텍스트 수정, 오타 교정, 주석·포맷팅·린트 정리, 로그 메시지 변경, 버전 번호만 올리는 커밋이 여기 해당합니다.
- 사소한 변경만으로 구성된 중간 업무나 큰 업무는 줄 자체를 만들지 않습니다. 커밋이 있다는 이유로 항목을 채우지 않습니다.
- 다만 기획·디자인 요청으로 내려온 문구 변경처럼 업무로 의뢰받은 건은 사소한 변경으로 보지 않고 `변경 반영`에 남깁니다.
- 상세가 한 줄뿐이면 상세 줄을 만들지 않고 중간 업무명에 합칩니다.
- 문체는 명사형 완료(`~ 적용`, `~ 처리`, `~ 추가`, `~ 수정`)로 씁니다.
- `feat:`, `fix:`, `chore:`, `refactor:`, `docs:`, `test:` 등 conventional commit 접두사를 제거합니다.
- 개발자 은어·변수명·파일 경로·커밋 해시를 노출하지 않고 업무 용어로 바꿉니다. (예: "null check 추가" → "빈 값 예외 처리")

재구성 예시:

```
수집 결과:
[Stock Link] (illunex/stock-link-mobile)
- feat: 종목 상세 차트 영역 퍼블리싱 ~9/8
  영역: stock/detail
  신호: 퍼블리싱
- fix: 종목 상세 반응형 레이아웃 깨짐 수정 ~9/9
  영역: stock/detail
  신호: 퍼블리싱
- feat: 종목 시세 조회 API 연동 ~9/10
  영역: stock/detail, 공통/api
  신호: API 연결

주간보고:
[Stock Link]
- 퍼블리싱 ~9/9 100%
  ◦ 종목 상세 페이지 100%
    : 차트 영역 마크업 및 스타일 적용 100%
    : 반응형 레이아웃 대응 100%
- API 연결 ~9/10 50%
  ◦ 종목 상세 페이지 50%
    : 시세 조회 연동 및 응답 처리 100%
    : 로딩·에러 상태 처리 0%
```

상세 `100%`와 `0%`의 평균은 `50%`이고, 10% 단위 내림도 `50%`이므로 중간·큰 업무가 모두 `50%`가 됩니다. 남은 `로딩·에러 상태 처리`는 금주 상세에 남겨 두되 차주 주간보고 항목으로도 내립니다.

## Step 8: 완료 여부와 진행률 판정

진행률은 **상세 업무부터 아래에서 위로** 판정합니다.

1. 상세 업무마다 확인된 작업 범위를 기준으로 10% 단위 진행률을 먼저 정합니다.
2. 중간 업무 진행률은 하위 상세 업무 진행률의 평균을 10% 단위로 **내림**한 값입니다. 상세 줄이 없는 중간 업무는 직접 판정합니다.
3. 큰 업무 진행률은 하위 중간 업무 진행률의 평균을 10% 단위로 **내림**한 값입니다.
4. 반올림이 아니라 내림을 쓰는 이유는, 하나라도 잔여 작업이 있으면 상위 항목이 완료로 보이지 않게 하기 위해서입니다.

### `100%`는 보수적으로

`100%`는 **후속 작업이 없다고 확인된 항목에만** 부여합니다. 아래 중 하나라도 해당하면 `90%` 이하로 잡습니다.

- 같은 화면·영역에 같은 주 안에서 수정 커밋이 반복됐고 아직 수렴했다고 볼 근거가 없음
- 다른 레포·라이브러리 릴리스에 맞춘 후속 반영이 남아 있음
- 개편·이행 작업의 일부만 반영됐고 나머지 화면·구간이 남아 있음
- 여러 화면·공통 모듈에 영향을 주는 변경인데 검증·QA 근거가 없음
- 사용자가 완료라고 밝히지 않았고, 커밋 제목만으로 완료 범위를 단정할 수 없음

완료 여부가 애매하면 `100%`가 아니라 `90%`를 기본값으로 씁니다. 커밋이 merge됐다는 사실만으로 `100%`를 주지 않습니다.

- 기능 완료, 배포, 최종 수정처럼 완료 근거가 명확한 항목만 `100%`로 표시합니다.
- 작업 중, 일부 구현, 후속 작업 필요, 임시 대응처럼 완료되지 않은 항목은 AI가 확인 가능한 작업 범위에 근거해 완성도를 대략 추정합니다.
- 추정 진행률은 `10%`, `20%`, `30%`처럼 반드시 10% 단위로 표시하고, 1% 단위의 정밀한 수치는 사용하지 않습니다.
- 작업 착수 근거가 전혀 없거나 사용자가 아직 시작하지 못했다고 밝힌 항목은 `0%`로 표시합니다.
- 완료 여부가 불명확해도 사용자 확인 때문에 보고 생성을 중단하지 않습니다. 임의로 `100%` 처리하지 말고 보수적인 10% 단위 진행률을 부여합니다.
- 사용자가 진행률을 명시하면 가장 가까운 10% 단위로 반올림해 사용합니다. 단, 사용자가 완료라고 명시한 경우에는 `100%`를 사용합니다.
- 전주 계획에서 이월된 항목은 전주 진행률을 시작값으로 사용하고, 금주 근거로 확인된 변화만 반영합니다.
- 전주 계획 항목에 관련 커밋이 없더라도 항목을 누락하지 않고 기존 진행률과 예상 종료일을 유지합니다.
- 관련 커밋이 있다는 사실만으로 `100%`로 판단하지 않습니다. 계획에 적힌 완료 범위가 충족됐다는 근거가 있어야 합니다.

진행률 추정 기준:

| 진행률 | 판단 기준 |
| --- | --- |
| `0%` | 아직 착수하지 못했거나 작업 시작 근거가 없는 단계 |
| `10~20%` | 조사·기획·환경 구성 또는 초기 착수 단계 |
| `30~40%` | 기본 구조와 일부 기능 구현 단계 |
| `50~60%` | 핵심 흐름의 절반 이상 구현 단계 |
| `70~80%` | 주요 기능 구현 완료, 보완·테스트·예외 처리 잔여 단계 |
| `90%` | 구현은 사실상 완료됐으나 최종 검증·리뷰·배포 중 하나 이상 잔여 |
| `100%` | 완료 근거가 명확하고 후속 필수 작업이 없는 상태 |

### 날짜 판정

- 큰 업무의 `~M/D`는 그 아래 모든 상세 업무 중 **가장 마지막 관련 작업일**을 사용합니다.
- 전주 계획에서 이월되어 금주에 `100%`가 된 항목은 마지막 관련 직접 커밋일 또는 PR merge 날짜를 실제 완료일 `~M/D`로 사용합니다.
- 완료된 이월 항목의 전주 예상 종료일은 실제 완료일로 반드시 교체하고, 예상 종료일을 완료일로 복사하지 않습니다.
- `100%` 미만 이월 항목은 전주 예상 종료일을 유지하되, 사용자가 종료일을 변경하면 갱신된 날짜를 사용합니다.
- 전주 계획 없이 커밋에서 새로 발견한 항목은 마지막 관련 직접 커밋일 또는 PR merge 날짜를 작업일로 사용합니다.
- 직접 커밋은 커밋 날짜, merge된 PR의 포함 커밋은 PR merge 날짜를 씁니다.

### 정렬

- 프로젝트 블록은 CLI 출력 순서(프로젝트 타이틀 오름차순)를 유지합니다.
- 프로젝트별 큰 업무는 `100%` 완료 항목을 먼저 배치하고 `100%` 미만 항목은 모두 맨 아래로 이동합니다.
- 완료 항목 그룹과 미완료 항목 그룹 내부에서는 각각 `~M/D` 날짜 오름차순으로 정렬합니다.
- 날짜까지 같으면 고정 어휘 순서(`퍼블리싱` → `API 연결` → `기능개발` → `버그 수정` → `리팩토링/구조 개선` → `배포/환경 설정` → `변경 반영`)를 따릅니다.
- 중간 업무는 관련 마지막 작업일 오름차순, 같으면 `영역:` 문자열 오름차순으로 정렬합니다.
- 상세 업무는 관련 작업일 오름차순으로 정렬합니다.

## Step 9: 현재 주간보고 출력 검증

출력 직전에 다음 조건을 항목별로 검사합니다.

1. 전주 계획의 모든 항목이 금주 보고에 포함됐는지 확인합니다.
2. 프로젝트명이 레포명이 아니라 HTML head 타이틀인지 확인합니다.
3. 모든 큰 업무가 고정 어휘 7종 중 하나이며 같은 프로젝트에서 중복되지 않는지 확인합니다.
4. 모든 큰 업무 줄이 `- 큰 업무명 ~M/D 진행률` 형식인지, 중간·상세 줄에 진행률이 빠지거나 날짜가 섞이지 않았는지 확인합니다.
4-1. 상위 항목 진행률이 하위 항목 평균의 10% 단위 내림값과 일치하는지 확인합니다.
4-2. 문구·라벨 수정 같은 사소한 변경이 상세 업무로 올라가 있지 않은지 확인합니다.
4-3. `100%`로 표시한 항목에 잔여 검증·후속 반영 근거가 남아 있지 않은지 확인합니다.
4-4. `100%` 미만 상세·중간 업무의 남은 범위가 차주 주간보고 항목으로 내려갔는지 확인합니다.
5. 들여쓰기가 큰 업무 0칸, 중간 업무 2칸 `◦ `, 상세 업무 4칸 `: `인지 확인합니다.
6. `100%`인 이월 항목은 `~M/D`가 실제 마지막 관련 커밋일 또는 PR merge 날짜인지 확인합니다.
7. 완료된 이월 항목에 전주 예상 종료일이 그대로 남아 있으면 실제 완료일로 교체합니다.
8. `100%` 미만 이월 항목은 기존 또는 갱신된 예상 종료일과 진행률을 유지했는지 확인합니다.
9. 계획 없이 새로 발견한 항목의 날짜가 없으면 CLI 원본에서 가장 마지막 작업일을 복원합니다.
10. 완료일을 예상 종료일이나 보고 생성일로 대체하지 않습니다.
11. 저장소별로 `100%` 미만 항목이 완료 항목보다 아래에 있는지 확인합니다.
12. 완료·미완료 그룹 내부가 각각 `~M/D` 날짜 오름차순인지 확인합니다.
13. 모든 항목의 포함 여부와 날짜·정렬 검증이 끝난 뒤에만 현재 주간보고를 확정합니다.

예시:

```text
전주 금주 계획:
- 테마 전환 기능 최종 검증 ~8/31 30%

금주 완료 근거:
- 관련 마지막 커밋 8/7, 완료 범위 충족

금주 주간보고:
[Stock Link]
- 기능개발 ~8/7 100%
  ◦ 설정 페이지 100%
    : 테마 전환 최종 검증 및 잔여 이슈 정리 100%
```

전주 예상 종료일 `8/31`은 완료 목표일일 뿐 실제 완료일이 아니므로 금주 완료 항목에 사용하지 않습니다.

## Step 10: 미완료 항목의 차주 주간보고 생성

현재 주간보고에 `100%` 미만 항목이 하나라도 있으면 차주 주간보고도 반드시 함께 제공합니다. 질문과 이월의 단위는 현재 보고와 같은 **큰 업무 줄**입니다.

### 잔여 작업은 차주로 내린다

- 금주 보고의 상세·중간 업무 중 `100%`가 아닌 항목은 **남은 범위를 차주 주간보고 항목으로 내려 적습니다.** 큰 업무만 이월하고 끝내지 않습니다.
- 금주 보고에는 이번 주에 확인된 작업만 적고, 이어서 진행할 단계는 금주 상세에 섞지 않고 차주 항목으로 분리합니다.
- 차주 항목의 중간·상세 업무명은 금주와 같은 이름을 씁니다. 이어지는 작업임을 알 수 있어야 합니다.
- 차주 항목에도 금주와 같이 큰·중간·상세 모든 줄에 진행률을 표시하고, 금주 진행률을 시작값으로 유지합니다.

1. `100%` 미만 항목만 추려 스킬 실행일과 기존 예상 종료일을 비교합니다.
2. 기존 예상 종료일이 실행일보다 미래인 항목은 질문 없이 기존 날짜로 차주 보고에 이월합니다.
3. 기존 예상 종료일이 실행일과 같거나 과거이거나 날짜가 없는 항목만 질문 대상으로 삼아 순서를 유지한 번호 목록을 만듭니다.
4. 질문 대상 항목의 예상 종료일을 사용자가 직접 입력할 수 있도록 한 항목당 하나의 질문을 제공합니다.
5. Claude Code·Cursor·Codex 어디서든 같은 방식으로 동작하도록 도구 전용 질문 UI나 API에 의존하지 말고 아래의 일반 텍스트 질문 형식을 사용합니다.
6. 여러 항목을 한 질문으로 뭉치지 않습니다. 사용자가 번호별 날짜를 한 번에 답할 수 있도록 모든 질문을 한 메시지에 나열합니다.
7. 질문 목록의 항목명은 `[프로젝트 타이틀] 큰 업무명` 형태로 적어 어느 프로젝트의 항목인지 구분합니다.
8. 사용자의 답변을 받은 뒤 질문 대상 항목을 차주 주간보고로 이월하고, 입력한 종료일을 `~M/D` 형식으로 반영합니다.
9. 종료일이 차주 범위를 벗어나더라도 사용자가 입력한 날짜를 유지합니다. 날짜가 모호하거나 유효하지 않을 때만 해당 항목을 다시 질문합니다.
10. 필요한 예상 종료일 답변을 받기 전에는 차주 주간보고를 확정하거나 날짜 없는 차주 항목을 출력하지 않습니다.
11. 차주 보고의 진행률은 예상값을 임의로 `100%`로 만들지 않습니다. 사용자가 목표 진행률을 주지 않았다면 현재 진행률을 유지하고 `예정`임을 표시합니다.
12. 차주 주간보고 바로 뒤에 `[미완료 판단 근거]`를 추가하고, 각 항목이 `100%`에 미치지 못했다고 판단한 근거를 한 줄로 짧게 설명합니다.
13. 판단 근거는 커밋·PR 제목이나 변경 맥락에서 확인된 잔여 작업만 언급합니다. 확인할 수 없는 세부 작업을 지어내지 않습니다.
14. 질문 대상 날짜 비교에는 보고 대상 주의 종료일이 아니라 실제 스킬 실행 날짜를 사용합니다.
15. 질문 대상인 `0%` 항목에는 예상 종료일과 함께 미착수 사유를 사용자가 직접 입력할 수 있는 추가 질문을 제공합니다.
16. 미착수 사유 질문에는 `기획 대기`, `디자인 대기`, `API 대기`, `기타 직접 입력`을 기본 옵션으로 제공하되 하나를 강제하지 않습니다.
17. 사용자가 입력한 미착수 사유는 항목명 바로 뒤 괄호에 짧게 반영합니다. 예: `기능개발(API 대기중)`.
18. Step 2의 전주 계획과 같은 업무 항목의 전주 진행률과 이번 진행률을 반드시 비교합니다.
19. 질문 대상이면서 이번 진행률이 `100%` 미만이고 전주 대비 증가 폭이 `0~10%p`이거나 진행률이 감소한 항목에는 변동 사유 질문을 추가합니다. 감소 폭과 관계없이 감소한 항목은 모두 질문합니다.
20. 변동 사유 질문에는 `기획 변경`, `API 변경`, `디자인 변경`, `우선순위 변경`, `기타 직접 입력`을 기본 옵션으로 제공합니다.
21. 진행률 비교는 `이번 진행률 - 전주 진행률`로 계산합니다. 예: `50% → 60%`는 `+10%p`, `60% → 50%`는 `-10%p`입니다.
22. 필요한 예상 종료일·미착수 사유·변동 사유 질문은 최종 차주 주간보고를 출력하기 전에 해당 항목별로 사용자 입력을 받습니다. 답변 전에는 사유를 임의로 선택하거나 최종 보고를 확정하지 않습니다.
23. 사용자가 입력한 변동 사유도 항목명 바로 뒤 괄호에 짧은 명사형으로 반영합니다. 예: `API 연결(기획 변경 반영)`.
24. 괄호 사유는 사용자의 입력을 우선하며, `대기` 사유는 `~ 대기중`, 변경 사유는 `~ 변경 반영`처럼 자연스럽게 다듬습니다.

질문 형식:

```text
차주 주간보고 작성을 위해 아래 미완료 항목을 입력해 주세요. (예: 1. 5/12)
1. [Stock Link] API 연결 — 종료일:
2. [Stock Link] 기능개발 — 종료일:

아직 시작하지 못한 아래 항목은 미착수 사유도 함께 입력해 주세요.
기본 옵션: 기획 대기 / 디자인 대기 / API 대기 / 기타 직접 입력
3. [Admin Console] 퍼블리싱 — 종료일: / 미착수 사유:

전주 대비 진행률 증가 폭이 0~10%p이거나 감소한 아래 항목은 변동 사유를 입력해 주세요.
기본 옵션: 기획 변경 / API 변경 / 디자인 변경 / 우선순위 변경 / 기타 직접 입력
4. [Admin Console] 기능개발 — 전주 50% → 이번 50% (0%p) / 변동 사유:
5. [Stock Link] 버그 수정 — 전주 60% → 이번 50% (-10%p) / 변동 사유:
```

사유 질문 생략 예시:

```text
스킬 실행일: 8/7
기존 예상 종료일: 8/31
현재 진행률: 0%
처리: 실행일이 예상 종료일보다 앞이므로 기존 종료일 8/31을 유지하고 종료일·미착수·변동 사유를 모두 질문하지 않음
```

차주 주간보고 형식(현재 주간보고와 같은 계층 구조를 사용하고, 상세 업무는 남은 작업이 명확할 때만 적습니다):

```text
[차주 주간보고]
[Stock Link]
- API 연결 ~5/12 80% (예정)
  ◦ 종목 상세 페이지 80%
    : 로딩·에러 상태 처리 80%
- 기능개발(API 대기중) ~5/15 0%
  ◦ 결제 내역 페이지 0%

[Admin Console]
- 퍼블리싱(기획 변경 반영) ~5/15 50%
  ◦ 정산 페이지 50%

[미완료 판단 근거]
- [Stock Link] API 연결: 시세 조회 연동은 반영됐으나 로딩·에러 처리 근거가 없어 80%로 판단
- [Stock Link] 기능개발: 결제 내역 화면 착수 내역이 없어 0%로 판단
- [Admin Console] 퍼블리싱: 전주 대비 진행률 변동이 없어 사용자에게 사유를 확인
```

미완료 항목이 없으면 종료일을 질문하지 않고 차주 주간보고도 생성하지 않습니다.

## Step 11: 연계 항목 정리

차주 주간보고 바로 뒤에 `[연계 항목]`을 붙여, **따로 보면 놓치는 연결을 한자리에 모읍니다.** 차주 작업을 판단할 때 함께 봐야 할 것이 무엇인지 드러내는 게 목적입니다.

정리 대상은 다음과 같습니다.

1. **금주 → 차주 연결**: 차주 항목이 금주 어느 프로젝트의 어느 큰 업무에서 이어지는지
2. **레포를 가로지르는 연결**: 공통 라이브러리·디자인 토큰·API 규격 변경처럼 한 레포의 작업이 다른 레포 반영을 부르는 관계
3. **같은 작업이 여러 프로젝트에 중복 반영된 건**: 같은 주에 여러 레포에 같은 내용이 들어간 경우
4. **선행·후행 관계**: 한쪽이 끝나야 다른 쪽을 진행할 수 있는 순서 의존

작성 규칙:

- 한 줄에 하나씩, `- <연계 주제>: <연결 관계>` 형식으로 적습니다.
- 프로젝트명은 금주 보고와 같은 `[프로젝트 타이틀]` 표기를 씁니다.
- 연결의 방향은 `→`로 표시합니다. (`[maintenance-kit] 기능개발 → [Stock Link] 배포/환경 설정`)
- 커밋·PR에서 확인되는 연결만 적고, 추측한 관계를 넣지 않습니다.
- 연결이 하나도 확인되지 않으면 `[연계 항목]` 섹션을 만들지 않습니다.

```text
[연계 항목]
- 에러 로그 수집: [maintenance-kit] 기능개발 → [Stock Link]·[Admin Console] 배포/환경 설정 (라이브러리 릴리스마다 앱 반영 필요)
- 디자인 토큰: [Stock Link] 퍼블리싱 → 차주 [Admin Console] 퍼블리싱 (토큰 확정 후 적용 가능)
```

## Step 12: 이슈사항 정리

마지막에 `[이슈사항]` 섹션을 붙입니다. 진행률로는 드러나지 않는 위험 요소를 따로 보게 하는 게 목적입니다.

이슈로 올리는 근거는 다음과 같습니다.

- 운영·프로덕션에서 발생한 장애나 그 대응 커밋
- 같은 화면·영역에 한 주 안에서 수정이 반복된 흔적 (원인 수렴이 덜 됐을 가능성)
- 보안 취약점·의존성 경고 대응
- 임시 대응·우회 처리로 남아 후속 정리가 필요한 부분
- 외부 릴리스·타 팀 응답·기획 확정 등 내 작업 밖의 대기 요인
- 같은 내용을 여러 레포에 수동으로 반복 반영하고 있는 구조

작성 규칙:

- `- <이슈>: <근거와 영향>` 한 줄 형식으로 적습니다.
- 커밋·PR에서 확인되는 사실만 적고, 심각도를 부풀리지 않습니다.
- 해결책을 단정하지 않습니다. 필요하면 `후속 확인 필요` 정도로 남깁니다.
- 확인된 이슈가 없으면 `[이슈사항]` 아래 `- 확인된 이슈 없음` 한 줄을 적습니다.

```text
[이슈사항]
- 프로덕션 화면 미마운트: [Stock Link] 소셜 분석 화면이 프로덕션에서 마운트되지 않아 당일 수정. 동일 원인 재발 여부 후속 확인 필요
- 개발 의존성 취약점: [maintenance-kit] 취약점 보고 의존성 갱신. 앱 레포 반영 여부 확인 필요
```

### 차주 주간보고 출력 검증

차주 주간보고를 출력하기 전에 모든 이월 항목에 기존 미래 종료일 또는 사용자가 새로 입력한 예상 종료일이 `~M/D`로 포함됐는지 검사합니다. 하나라도 누락되면 차주 보고를 확정하지 않고 누락된 질문 대상 항목의 종료일만 다시 질문합니다.

## Step 13: HTML 표 산출물

사용자가 주간보고를 **표**·**테이블**·**HTML**로 요청하면("주간보고 표로 만들어줘", "주간보고 테이블 만들어줘" 등) 텍스트 보고 대신 아래 규격의 HTML 표를 만듭니다. 팀 전체 취합본을 사내 페이지·위키에 올릴 때 쓰는 형식입니다.

템플릿: `skills/weekly-report/assets/report-table-template.html`

이 파일을 복사한 뒤 `PERIOD`, `<h1>`, `DATA`, `PROJECT_ORDER`, 하단 3개 노트 섹션만 교체합니다. 스타일과 렌더링 로직은 손대지 않습니다.

### 표 구조

| 열 | 내용 |
| --- | --- |
| 프로젝트명 | 1열. **프로젝트 기준으로 행을 병합**한다. 담당자 기준으로 묶지 않는다 |
| 담당자 | 2열. 같은 프로젝트를 여러 명이 맡으면 병합된 프로젝트 셀 안에 담당자 행이 쌓인다 |
| 금주 업무 | 3열. 큰 → 중간 → 상세 3단계를 셀 안에 그대로 넣는다 |
| 차주 업무 | 4열. 이월·신규 계획. 없으면 `이월 항목 없음` |
| 이슈사항 | 5열. Step 12 기준(운영 장애, 반복 수정, 보안·의존성 경고, 임시 대응, 외부 대기 요인)에 해당하는 문장만 불릿으로 나열. 없으면 `확인된 이슈 없음` |

- 금주 업무가 없고 차주 계획만 있는 프로젝트도 행을 만들고 금주 칸은 `—`로 둡니다.
- 프로젝트 정렬은 `PROJECT_ORDER`에 적은 순서를 먼저 따르고, 목록에 없는 프로젝트는 뒤에 붙입니다.
- 이슈사항은 계층 없이 문장 단위 불릿으로만 적습니다. 금주·차주 업무 항목을 그대로 되풀이하지 않고, Step 12 기준에 해당하는 근거만 추려 적습니다.

### 진행률 강조 단계

진행률은 세 단계 모두 표시하되 **계층이 깊어질수록 강조를 약하게** 합니다. 한 셀 안에서 대분류가 먼저 읽히게 하는 게 목적입니다.

| 계층 | 표기 |
| --- | --- |
| 대분류(큰 업무) | 배경색 뱃지 |
| 중분류(중간 업무) | 굵은 글씨, 배경 없음 |
| 소분류(상세 업무) | 일반 글씨 |

- 색은 `100%`면 초록(`#1c6742` / `#e2f0e8`), `100%` 미만이면 주황(`#8f5400` / `#fbeeda`)을 세 단계 모두 같게 씁니다. 강조 차이는 배경과 굵기로만 냅니다.

### 날짜 표기 세 가지

| 값 | 렌더링 | 쓰는 경우 |
| --- | --- | --- |
| `"9/18"` | `~9/18` | 완료일 또는 예상 종료일 |
| `"상시 진행"` | `상시 진행` | 이슈 대응처럼 프로젝트 종료까지 이어지는 업무 |
| `null` | `종료일 미정` | 사용자가 일정 미정이라고 확인한 항목 |

`null`은 사용자에게 종료일을 물어보기 전 임시값으로 쓰지 않습니다. Step 10의 질문을 먼저 끝내고, 사용자가 미정이라고 답한 경우에만 `null`로 둡니다.

### 인라인 스타일 원칙

**`<table>` 안쪽 모든 요소는 인라인 스타일만 씁니다.** 표만 복사해 다른 도메인에 붙여 넣어도 그대로 보여야 하기 때문입니다.

- 클래스·CSS 변수·외부 스타일시트에 의존하지 않고 리터럴 색상값을 직접 씁니다.
- `::before` 같은 가상요소를 쓰지 않습니다. 복사되지 않습니다. `◦`·`:` 마커는 실제 `<span>`으로 넣습니다.
- **표 내부 인라인 스타일에는 `font-family`를 넣지 않습니다.** 따옴표가 든 폰트명(`"IBM Plex Mono"` 등)을 `style="..."` 속성값 안에 그대로 넣으면 속성을 감싸는 큰따옴표와 충돌해 그 뒤 인라인 스타일 전체가 깨집니다. 붙여 넣는 쪽 문서의 기본 폰트를 그대로 따르게 둡니다.
- 표 바깥(헤더, 범례, 하단 노트)도 같은 이유로 커스텀 웹폰트를 쓰지 않고 시스템 폰트만 사용합니다.
- 표 위에 `표 HTML 복사` 버튼을 두고 `text/html`·`text/plain`을 함께 클립보드에 넣습니다. 클립보드 API가 막히면 표를 선택 상태로 만드는 폴백을 둡니다.

### 하단 노트 3종

표 아래에 다음 섹션을 붙입니다. 해당 내용이 없으면 그 섹션은 만들지 않습니다.

1. `일정 미확정 항목` — 종료일·진행률을 확정하지 못한 항목과 그 사유
2. `미완료 판단 근거` — Step 10의 판단 근거를 그대로 옮김
3. `표기 정리 기준` — 프로젝트명 통일, 큰 업무 배정이 갈린 건, 내부 용어 치환 내역

## Failure Handling

| 오류 메시지 | 조치 |
| --- | --- |
| `GitHub CLI (gh) is required` | macOS는 `brew install gh`, Windows는 `winget install GitHub.cli` 또는 공식 설치 파일로 설치 후 재시도 |
| `jq is required` | macOS는 `brew install jq`, Windows는 `winget install jqlang.jq` 또는 공식 설치 파일로 설치 후 재시도 |
| `GitHub CLI is not authenticated` | `gh auth login` 실행 후 재시도 |
| `해당 기간 커밋 없음` | 날짜 범위 확인. `--week 1`로 지난주 시도 |
| `[경고] 결과가 N건 상한에 도달했습니다` | `--limit` 값을 올리거나 `--from`/`--to`로 범위를 좁힘 |
| `[경고] ... 변경 파일 조회에 실패해 건너뜁니다` | 해당 커밋은 `영역:`·`신호:` 없이 커밋 메시지만으로 분류. 반복되면 레포 접근 권한 확인 |
| 프로젝트 타이틀이 레포명으로 표시됨 | `--refresh-titles`로 재조회하거나 사용자에게 정식 프로젝트명을 확인 |
