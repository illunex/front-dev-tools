# weekly-report

이번 주(또는 특정 주)에 GitHub에 커밋한 내역과 기간 내 merge된 내가 연 PR의 포함 커밋을 주간보고 포맷으로 정리합니다.

## 사용 시점

다음과 같은 요청이 왔을 때 이 skill을 사용합니다:

- "주간보고 정리해줘" / "주간 작업 내역 뽑아줘"
- "이번주 커밋 정리해줘" / "이번주에 뭐 했는지 보여줘"
- "지난주 작업 내역" / "저번주 커밋 요약"
- "weekly report" / "weekly summary"

## 출력 포맷

```
[owner/repo]
- 커밋 subject ~M/D 100%
- 커밋 subject ~M/D 100%

[owner/repo2]
- 커밋 subject ~M/D 100%
```

- 기간 기본값: 요청 시점을 포함하는 ISO 주(월~일)
- 완료로 판단되는 항목만 `100%`로 표시
- 완료되지 않았거나 완료 근거가 부족한 항목은 AI가 완성도를 추정해 반드시 10% 단위의 `100%` 미만 진행률로 표시하고, 미착수 항목은 `0%`로 표시
- merge / revert 커밋은 자동 제외
- 같은 repo 내 동일 subject는 중복 제거
- 직접 커밋은 커밋 날짜, merge된 PR의 포함 커밋은 PR merge 날짜로 표시
- 현재 주간보고의 `~M/D`는 작업일, 차주 주간보고의 `~M/D`는 사용자가 입력한 예상 종료일을 의미하며 생략하지 않음

## Prerequisites

1. **Bash 실행 환경** — macOS/Linux 터미널 또는 Windows Git Bash/WSL
2. **GitHub CLI(`gh`) 설치** — macOS는 `brew install gh`, Windows는 `winget install GitHub.cli` 또는 [cli.github.com](https://cli.github.com)
3. **gh 인증** — `gh auth login` 완료
4. **jq 설치** — macOS는 `brew install jq`, Windows는 `winget install jqlang.jq` 또는 [jq 다운로드](https://jqlang.github.io/jq/download/)

## Step 1: weekly-report CLI 설치 확인

```bash
command -v weekly-report
```

CLI가 없으면 **사용자에게 다음 설치 명령을 제안하고 동의를 받은 뒤 실행**합니다:

```bash
curl -fsSL https://raw.githubusercontent.com/illunex/front-dev-tools/main/install/install-weekly-report.sh | bash
```

설치 경로는 기본적으로 `~/.local/bin/weekly-report`입니다. 설치 후 `~/.local/bin`이 `PATH`에 없다면 셸 프로필에 아래 줄을 추가해야 합니다:

```bash
export PATH="$HOME/.local/bin:$PATH"
```

## Step 2: 인자 추론

사용자 요청에서 다음 인자를 추론합니다:

| 인자 | 추론 방법 | 기본값 |
| --- | --- | --- |
| `--week <n>` | "지난주" → `1`, "이번주" → `0` | `0` |
| `--from`, `--to` | 특정 날짜를 명시한 경우 사용 | 자동 계산(ISO week) |
| `--author <login>` | 다른 사람의 내역 요청 시 지정 | 인증된 사용자 |
| `--limit <n>` | 직접 커밋 또는 merge된 PR이 많을 것으로 예상될 때 조정 | `200` |

## Step 3: 실행

```bash
# 이번 주 (기본)
weekly-report

# 지난주
weekly-report --week 1

# 특정 날짜 범위
weekly-report --from 2026-04-13 --to 2026-04-19

# 다른 사용자
weekly-report --author octocat
```

CLI는 직접 커밋 검색 결과와, 같은 기간에 merge된 `--author` 사용자의 PR에 포함된 커밋을 함께 수집합니다.

## Step 4: 완료 여부와 진행률 판정

각 항목의 커밋·PR 제목과 변경 맥락을 바탕으로 완료 여부를 먼저 판정합니다.

- 기능 완료, 배포, 최종 수정처럼 완료 근거가 명확한 항목만 `100%`로 표시합니다.
- 작업 중, 일부 구현, 후속 작업 필요, 임시 대응처럼 완료되지 않은 항목은 AI가 확인 가능한 작업 범위에 근거해 완성도를 대략 추정합니다.
- 추정 진행률은 `10%`, `20%`, `30%`처럼 반드시 10% 단위로 표시하고, 1% 단위의 정밀한 수치는 사용하지 않습니다.
- 작업 착수 근거가 전혀 없거나 사용자가 아직 시작하지 못했다고 밝힌 항목은 `0%`로 표시합니다.
- 완료 여부가 불명확해도 사용자 확인 때문에 보고 생성을 중단하지 않습니다. 임의로 `100%` 처리하지 말고 보수적인 10% 단위 진행률을 부여합니다.
- 사용자가 진행률을 명시하면 가장 가까운 10% 단위로 반올림해 사용합니다. 단, 사용자가 완료라고 명시한 경우에는 `100%`를 사용합니다.

진행률 추정 기준:

| 진행률 | 판단 기준 |
| --- | --- |
| `0%` | 아직 착수하지 못했거나 작업 시작 근거가 없는 단계 |
| `10~20%` | 조사·기획·환경 구성 또는 초기 착수 단계 |
| `30~40%` | 기본 구조와 일부 기능 구현 단계 |
| `50~60%` | 핵심 흐름의 절반 이상 구현 단계 |
| `70~80%` | 주요 기능 구현 완료, 보완·테스트·예외 처리 잔여 단계 |
| `90%` | 구현은 사실상 완료됐으나 최종 검증·리뷰·배포 중 하나 이상 잔여 |
| `100%` | 완료 근거가 명확하고 후속 필수 작업이 없는 상태 |

## Step 5: 주간보고용 문장으로 재구성

CLI 출력을 그대로 사용자에게 보여주지 말고, **각 항목을 주간보고용 한국어 문장으로 재작성**한 뒤 출력합니다.

재작성 규칙:

- `feat:`, `fix:`, `chore:`, `refactor:`, `docs:`, `test:` 등 conventional commit 접두사 제거
- 개발자 은어·내부 변수명은 업무 용어로 변환 (예: "null check 추가" → "안정성 개선")
- 한 레포 안에서 같은 기능에 속하는 커밋 여러 개는 하나의 항목으로 묶어 표현
- 문체: **명사형 완료** (예: "~기능 개발", "~버그 수정", "~개선")
- 현재 주간보고의 모든 항목에 작업일을 `~M/D`로 표시
- 직접 커밋은 커밋 날짜를 작업일로 사용하고, merge된 PR의 포함 커밋은 PR merge 날짜를 작업일로 사용
- 여러 커밋을 하나의 업무로 묶으면 가장 마지막 관련 작업일을 사용
- Step 4에서 판정한 진행률 유지

재구성 예시:

```
원본:
[illunex/my-project]
- feat: 사용자 인증 기능 추가 ~4/21 100%
- fix: 로그인 시 null 포인터 예외 처리 ~4/22 100%
- fix: 토큰 만료 후 리다이렉트 누락 수정 ~4/22 100%

재구성:
[illunex/my-project]
- 사용자 인증 기능 개발 ~4/21 100%
- 로그인 안정성 개선 ~4/22 100%
```

레포 이름(`[owner/repo]`)과 날짜·진행률 포맷은 그대로 유지합니다.

### 현재 주간보고 출력 검증

출력 직전에 다음 조건을 항목별로 검사합니다.

1. 모든 항목이 `- 업무명 ~M/D 진행률` 형식인지 확인합니다.
2. `~M/D`가 없으면 CLI 원본에서 해당 업무의 가장 마지막 작업일을 복원합니다.
3. 날짜를 복원할 근거가 없으면 날짜 없는 항목을 출력하지 말고, 해당 저장소·커밋 원본을 다시 조회합니다.
4. 작업일을 예상 종료일이나 보고 생성일로 대체하지 않습니다.
5. 모든 항목의 날짜 검증이 끝난 뒤에만 현재 주간보고를 확정합니다.

## Step 6: 미완료 항목의 차주 주간보고 생성

현재 주간보고에 `100%` 미만 항목이 하나라도 있으면 차주 주간보고도 반드시 함께 제공합니다.

1. `100%` 미만 항목만 추려 순서를 유지한 번호 목록을 만듭니다.
2. 각 항목의 예상 종료일을 사용자가 직접 입력할 수 있도록 한 항목당 하나의 질문을 제공합니다.
3. Claude Code·Cursor·Codex 어디서든 같은 방식으로 동작하도록 도구 전용 질문 UI나 API에 의존하지 말고 아래의 일반 텍스트 질문 형식을 사용합니다.
4. 여러 항목을 한 질문으로 뭉치지 않습니다. 사용자가 번호별 날짜를 한 번에 답할 수 있도록 모든 질문을 한 메시지에 나열합니다.
5. 사용자의 답변을 받은 뒤 각 미완료 항목을 차주 주간보고로 이월하고, 입력한 종료일을 `~M/D` 형식으로 반영합니다.
6. 종료일이 차주 범위를 벗어나더라도 사용자가 입력한 날짜를 유지합니다. 날짜가 모호하거나 유효하지 않을 때만 해당 항목을 다시 질문합니다.
7. 예상 종료일 답변을 받기 전에는 차주 주간보고를 확정하거나 날짜 없는 차주 항목을 출력하지 않습니다.
8. 차주 보고의 진행률은 예상값을 임의로 `100%`로 만들지 않습니다. 사용자가 목표 진행률을 주지 않았다면 현재 진행률을 유지하고 `예정`임을 표시합니다.
9. 차주 주간보고 바로 뒤에 `[미완료 판단 근거]`를 추가하고, 각 항목이 `100%`에 미치지 못했다고 판단한 근거를 한 줄로 짧게 설명합니다.
10. 판단 근거는 커밋·PR 제목이나 변경 맥락에서 확인된 잔여 작업만 언급합니다. 확인할 수 없는 세부 작업을 지어내지 않습니다.
11. `0%` 항목에는 예상 종료일과 함께 미착수 사유를 사용자가 직접 입력할 수 있는 추가 질문을 제공합니다.
12. 미착수 사유 질문에는 `기획 대기`, `디자인 대기`, `API 대기`, `기타 직접 입력`을 기본 옵션으로 제공하되 하나를 강제하지 않습니다.
13. 사용자가 입력한 미착수 사유는 항목명 바로 뒤 괄호에 짧게 반영합니다. 예: `결제 내역 화면 개발(API 대기중)`.
14. 전주 주간보고가 함께 제공되면 같은 레포·같은 업무 항목의 전주 진행률과 이번 진행률을 비교합니다.
15. 이번 진행률이 `100%` 미만이면서 전주 대비 증가 폭이 `0~10%p`이거나 진행률이 감소한 항목에는 변동 사유 질문을 추가합니다. 감소 폭과 관계없이 감소한 항목은 모두 질문합니다.
16. 변동 사유 질문에는 `기획 변경`, `API 변경`, `디자인 변경`, `우선순위 변경`, `기타 직접 입력`을 기본 옵션으로 제공합니다.
17. 진행률 비교는 `이번 진행률 - 전주 진행률`로 계산합니다. 예: `50% → 60%`는 `+10%p`, `60% → 50%`는 `-10%p`입니다.
18. 미착수 사유와 변동 사유 질문은 최종 차주 주간보고를 출력하기 전에 해당 항목별로 사용자 입력을 받습니다. 답변 전에는 사유를 임의로 선택하거나 최종 보고를 확정하지 않습니다.
19. 사용자가 입력한 변동 사유도 항목명 바로 뒤 괄호에 짧은 명사형으로 반영합니다. 예: `결제 내역 화면 개발(기획 변경 반영)`.
20. 괄호 사유는 사용자의 입력을 우선하며, `대기` 사유는 `~ 대기중`, 변경 사유는 `~ 변경 반영`처럼 자연스럽게 다듬습니다.

질문 형식:

```text
차주 주간보고 작성을 위해 아래 미완료 항목을 입력해 주세요. (예: 1. 5/12)
1. 사용자 인증 기능 개발 — 종료일:
2. 로그인 안정성 개선 — 종료일:

아직 시작하지 못한 아래 항목은 미착수 사유도 함께 입력해 주세요.
기본 옵션: 기획 대기 / 디자인 대기 / API 대기 / 기타 직접 입력
3. 결제 내역 화면 개발 — 종료일: / 미착수 사유:

전주 대비 진행률 증가 폭이 0~10%p이거나 감소한 아래 항목은 변동 사유를 입력해 주세요.
기본 옵션: 기획 변경 / API 변경 / 디자인 변경 / 우선순위 변경 / 기타 직접 입력
4. 정산 화면 개발 — 전주 50% → 이번 50% (0%p) / 변동 사유:
5. 알림 기능 개발 — 전주 60% → 이번 50% (-10%p) / 변동 사유:
```

차주 주간보고 형식:

```text
[차주 주간보고]
[owner/repo]
- 사용자 인증 기능 개발 ~5/12 80% (예정)
- 결제 내역 화면 개발(API 대기중) ~5/15 0%
- 정산 화면 개발(기획 변경 반영) ~5/15 50%

[미완료 판단 근거]
- 사용자 인증 기능 개발: 핵심 인증 흐름은 구현됐으나 예외 처리와 통합 테스트 완료 근거가 없어 80%로 판단
- 결제 내역 화면 개발: 작업 착수 내역이 없어 0%로 판단
- 정산 화면 개발: 전주 대비 진행률 변동이 없어 사용자에게 사유를 확인
```

미완료 항목이 없으면 종료일을 질문하지 않고 차주 주간보고도 생성하지 않습니다.

### 차주 주간보고 출력 검증

차주 주간보고를 출력하기 전에 모든 이월 항목에 사용자가 입력한 예상 종료일이 `~M/D`로 포함됐는지 검사합니다. 하나라도 누락되면 차주 보고를 확정하지 않고 누락된 항목의 종료일만 다시 질문합니다.

## Failure Handling

| 오류 메시지 | 조치 |
| --- | --- |
| `GitHub CLI (gh) is required` | macOS는 `brew install gh`, Windows는 `winget install GitHub.cli` 또는 공식 설치 파일로 설치 후 재시도 |
| `jq is required` | macOS는 `brew install jq`, Windows는 `winget install jqlang.jq` 또는 공식 설치 파일로 설치 후 재시도 |
| `GitHub CLI is not authenticated` | `gh auth login` 실행 후 재시도 |
| `해당 기간 커밋 없음` | 날짜 범위 확인. `--week 1`로 지난주 시도 |
